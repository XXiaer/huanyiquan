# 换一圈 · 校园以物换物平台（后端）

按《换一圈 · 产品需求文档 v1.0》落地的 Java 后端。核心是三方换物环：一对一谈不成的两个人，靠第三个人凑成闭环，一次全成。

## 一、技术栈：严格照着文档来

| 文档要求（第十一节） | 本项目的做法 |
| --- | --- |
| servlet / service / dao / entity 四层分包 | `com.huanyiquan` 下同名四个包，另加 `common`、`filter`、`listener` |
| 原生 JDBC + 手动事务 | `DBUtil` 封装连接与 `tx()`，事务内 commit / rollback 全手写 |
| MySQL 8 | `sql/schema.sql`，utf8mb4 |
| 全部 SQL 走 PreparedStatement | DAO 里没有任何字符串拼接参数 |
| session 存 userId，Filter 统一拦截 | `LoginFilter` 白名单 + `AdminFilter` 角色二次校验 |
| 统一返回体 `{code, msg, data}` | `Result` + `BaseServlet` 统一异常转换 |

没有用 Spring，也没有用 MyBatis。JDK 11 编译，Servlet 6.0（jakarta 包名，对应 Tomcat 10.1）。

为了省掉"装 Tomcat、配 war 包"这一步，项目带了一个内嵌 Tomcat 启动类 `Application`，`mvn exec:java` 直接跑。同时保留 `war` 打包和 `WEB-INF/web.xml`，需要交给学校统一部署时也能用。

## 三、三步跑起来

**第 1 步：建库**

```bash
mysql -uroot -p < sql/schema.sql
```

**第 2 步：改密码**

打开 `src/main/resources/db.properties`，把 `db.password` 改成你自己 MySQL 的密码。也可以用环境变量 `DB_URL` / `DB_USER` / `DB_PASSWORD` 覆盖。

**第 3 步：启动**

最省事的方式：双击项目根目录的 `start.bat`。它会自动编译、启动内嵌 Tomcat，并在窗口里打印地址和账号。关掉窗口即停服务。

习惯命令行的还是用：

```bash
mvn clean compile exec:java
```

看到 `换一圈 后端已启动：http://localhost:8080` 就成了。首次启动会自动建一个管理员：`admin / admin123`。

**随手自检**

```bash
python scripts/health.py
```

会依次检查 MySQL 端口、后端接口、静态页面、登录鉴权、三方环匹配，逐条打 `[OK]` 或 `[X]`，最后给结论。只读，不改数据。

**第 4 步：打开页面**

浏览器访问 `http://localhost:8080`，前后端同源，不用配代理，也不用另起前端服务。

想打成 war 交给学校 Tomcat：`mvn package`，把 `target/huanyiquan.war` 丢进 Tomcat 10.1 的 webapps。前端已经在 webapp 根目录，一起打进去了。

## 四、三十秒跑通核心功能

1. 用管理员登录：`POST /api/user/login`，`{"studentNo":"admin","password":"admin123"}`
2. 造演示数据：`POST /api/admin/demo`，会生成小林、阿哲、雨桐三个人和三件物品，三件意向正好首尾相接。返回里带 `itemIds`。
3. 换成小林登录（`2021210001 / 123456`），请求 `GET /api/cycle/{机械键盘的 id}`，就能看到一条三方环和推荐面交点。
4. `POST /api/cycle/{id}/create`，body `{"itemIds":[键盘id, 耳机id, 球拍id]}`，正式成环，三件物品立刻变"锁定"。
5. 三个账号分别 `POST /api/exchange/{exchangeId}/confirm`，第三个人确认后状态变"待交付"。
6. 三人分别 `POST /api/exchange/{exchangeId}/done`，最后一个人点完，物品变"已换出"，各人信用分 +2。
7. 互相 `POST /api/review`，打分，被评人信用分按"星级 − 3"微调。

## 五点五、账号规则

- **学号必须是 10 位数字**，注册时前端和后端各校验一次（`^\d{10}$`），提示"学号是 10 位数字，例如 2021210001"。登录不校验格式，保证历史账号还能进。
- 平台归属：**重庆移通学院**。登录页、个人主页、页面标题都带校名。
- 密码 6-20 位，SHA-256 加盐存储。

## 五点六、物品上架

一条完整的发布链路，前后端都验过：

| 环节 | 实现 |
| --- | --- |
| 入口 | 三个：底部导航中间的「发布」、集市「精选好物」标题右侧的「＋ 上架」、我的「我的物品」标题右侧的「＋ 上架」 |
| 必填 | 名称 ≤30、类别、成色、想换什么（环匹配的原料） |
| 选填 | 描述 ≤300（带字数计数）、期望说明 ≤100、图片最多 3 张 |
| 图片 | 先传 `/api/upload` 拿路径，提交时逗号拼进 `images`；上传后显示缩略图，可单张删除 |
| 校验 | 信用分 ≥60、在架 ≤20 件、敏感词、同名 1 分钟内去重 |
| 上下架 | 两处都能操作：① 我的 →「我的物品」按状态筛选（全部 / 在架 / 已下架 / 已换出），在架点「下架」，已下架点「重新上架」；② 物品详情页，主人视角下已下架时底部直接给「重新上架」 |

实测链路：上传 1×1 PNG → 带图上架 → 详情 `images` 字段正确 → 图片可取回（`image/png`）→ 下架 → 重新上架，全部 200。

## 五点七、登录页自带连通检测

打开登录页就会调一次 `GET /api/meta/status`，卡片里显示两行：

```
● 后端    已连接
● 数据库  正常 · 在架 3 件
```

任何一行变红都能直接看出是哪一层断了：后端没起提示"双击 start.bat"，数据库没连提示"检查 MySQL 与 db.properties"，下面是「重新检测」。

点登录时走的还是真实登录 + `/api/user/me` 复核，等于把「前端 → 后端 → 数据库」整条链走了一遍。数据库出错时，错误提示会被翻译成"数据库连不上：确认 MySQL 已启动，且 db.properties 里的账号密码正确"。

`/api/meta/status` 是公开接口，不需要登录，只做只读查询，数据库挂了也正常返回 `db:false` 而不是 500。

## 六、状态常量（写死在 `Const` 里，代码只能单向推进）

- 物品 `item.status`：1 在架 / 2 锁定 / 3 已换出 / 4 已下架
- 报价 `offers.status`：0 待响应 / 1 已接受 / 2 已拒绝 / 3 已失效 / 4 已撤回 / 5 已还价关闭
- 交换单 `exchange.status`：1 待确认 / 2 待交付 / 3 已完成 / 4 已失效 / 5 已超时关闭

交换单是全系统最容易出事的对象。它一旦卡住，物品就永远锁在"2 锁定"里。所以三个动作都包在事务里：落单、状态推进、信用结算。

## 七、环匹配到底怎么算

找的是：我把 I0 给 B，B 把 I1 给 C，C 把 I2 给我。三次查询：

1. **谁想要我这件**：`intent` 里 `want_item_id = I0` 或同类别的人，得到 `(B, I1)`。
2. **我想要的东西在谁手上**：按 I0 的意向找出满足条件的物品，得到 `(C, I2)`。
3. **验证第三条边**：C 有没有表示想要 I1（必须是 C 用 I2 这件物品表达出的意向，不是他别的物品）。

匹配只读，不加锁，最多返回 3 组；单次最多检查 300 个组合，防止关系表大了拖死库。真正锁物品是在 `POST /api/cycle/{itemId}/create` 的事务里，锁之前再核一次三件物品状态。

## 八、定时任务

`TaskListener` 起一个守护线程池：

- 每 5 分钟：把超过 24 小时还没响应的报价改成"已失效"。
- 每 10 分钟：待确认超 24 小时的交换单整单失效、物品解锁；待交付超 7 天的单子超时关闭，未确认方信用分 −3。
- 每 10 分钟：刷新敏感词缓存。

这些不依赖用户在线，答辩时关掉浏览器也会照常跑。

## 九、和文档不一致的地方（主动交代）

1. **收藏功能没做**。文档 F-08 提到收藏，但数据表设计里正好 9 张表，没有收藏表。加表就破了你答辩时说的"9 张表"，所以留到二期。
2. **多了一张 `biz_log`**。UC-07 要求"所有状态变化写日志表"，所以这是第 10 张，表设计那节可以口头补一句。
3. **加了两个文档没写的接口**：`/api/exchange/{id}/cancel`（UC-06 说任一方可拒绝，需要一个入口）和 `/api/cycle/{itemId}/create`（文档写"命中即落单"，但匹配不该带写锁，所以拆成"先找、再确认成环"两步）。
4. **图片上传是我补的**。文档只写"只存路径"，没说文件怎么进来。
5. **还价**按文档"反过来用自己另一件物品去换对方的物品"实现：原报价关闭，生成一条方向相反的新报价，`parent_id` 指回上一条。
6. 密码用 SHA-256 加盐，不是 BCrypt。课程项目够用，生产该换。

## 十、验收标准自查

| 文档验收项 | 对应的实现 |
| --- | --- |
| 两个账号走完一对一 | `POST /api/offer` → `handle(accept)` → 两次 `done` |
| 三个账号走完三方环 | `GET /api/cycle/{id}` → `create` → 三次 `confirm` → 三次 `done` |
| 任一方拒绝，整单失效物品解锁 | `POST /api/exchange/{id}/cancel`，事务内解锁三件物品 |
| 报价 24 小时自动失效 | 定时任务每 5 分钟扫一次 |
| 未登录 401、越权 403 | `LoginFilter` + 每个写接口的归属校验 |
| 后台看举报、下架物品 | `GET /api/admin/report` → `handle(approve)` |

## 十一、前端

### 视觉方向

界面参考清新电商风：浅薄荷底 `#F5FAF1`、草绿主色 `#2E9E4B`、红色强调数字 `#F5402F`、大圆角卡片（16 / 22）、顶部渐层 banner。

三处是刻意换掉的电商语言：

- 商品卡的"价格"位置换成**信用分**（红色加粗），旁边是"类别 · 报价数"。换物没有价格，但有等价的可信度。
- 首屏 banner 不讲折扣，讲**「三件闲置换一圈」**，右侧是往返箭头徽标。
- 活动条从"领券"改成**"两个人换不成？凑三方环"**，直接指向核心功能。

颜色、字号、间距全部走 CSS 变量，改 `:root` 一处就能换肤；旧的 `--brand-*` 变量名保留为别名，历史样式不会失效。

### 为什么不用框架

三个人的课程项目，装 Node、配 Vite、管依赖，比写页面本身还费时间。所以前端是原生 HTML + CSS + JS，零依赖、零构建，改完刷新就生效。代价是没有组件复用，所以样式全部收进 `app.css` 的变量和组件类里。

### 几个交互上的取舍

- **一件事只给一个主按钮。** 详情页底部是「用我的物品换」，举报收成次要按钮；交换单里是「我已交换」，约面交和取消并排在下面。
- **状态用颜色说话。** 物品锁定后整张卡片降到 62% 透明度，锁着的卡片一眼看出来点不动，不用读文字。
- **数字等宽。** 信用分、计数、件数全部 `tabular-nums`，列表扫视时不跳。
- **每个空状态都给出下一步。** 没有物品就给「去发布」，没有报价就给「去集市」，不留白屏。
- **401 统一跳登录。** `api()` 里拦一次，任何接口过期都回到登录页，不用每个页面写判断。

## 十二、三端联调记录

这一节记录的是**实际跑过**的结果，不是设计意图。环境：Windows 11、JDK 11.0.26、MySQL 8.0.46（127.0.0.1:3306）。

### 1. 数据库


### 6. 登录态为什么能跨重启

一开始登录用的纯 session：`HttpSession` 存在内存里，服务一重启就没了，登录状态跟着丢。表现就是"登录进去点了半天，发布的时候突然让我重新登录"。

现在登录时会额外发一个签名 cookie：

```
hq_token = userId.expireAtMillis.HmacSHA256(userId.expireAtMillis, app.secret)
```

`LoginFilter` 发现 session 里没有 userId 时，先验这个 cookie 的签名和过期时间，对得上就顺手把 session 重建出来，请求照常放行。所以重启服务、甚至重启电脑，七天内都不用重新登录。

安全上的取舍：

- cookie 是 `HttpOnly` + `Path=/`，前端脚本读不到。
- 只签用户 id 和过期时间，不放昵称、学号。
- 签名密钥在 `db.properties` 的 `app.secret`，换一个值等于让所有人重新登录一次。
- 退出登录会把这个 cookie 一起清掉。
- 伪造凭证过不了签名校验，实测返回 401。

另外前端补了两处，让掉登录这件事不那么难受：

- 401 时记住当前页面，重新登录后自动跳回去，不是每次都回首页。
- 发布前把表单内容存进 `sessionStorage`，重登回来还能接着发，不用重填。

### 7. 关于"重启后掉登录"的实测

| 场景 | 结果 |
| --- | --- |
| 登录后直接发布 | 200，跳到新物品详情页 |
| 登录 → 杀掉服务 → 重启 → 再发布 | 200，登录态自动恢复 |
| 不带任何凭证发布 | 401「登录状态已失效，请重新登录」 |
| 伪造 `hq_token` | 401，签名校验拦住 |

### 8. 鉴权不再依赖 Cookie

上一版把凭证放在 `hq_token` cookie 里，遇到浏览器禁用 Cookie（无痕模式、隐私插件、站点设置）就会：登录看着成功，但下一个需要鉴权的请求 401，于是点哪儿都弹回登录页。

现在双通道：

- 登录响应同时给 `Set-Cookie: hq_token` 和响应头 `X-Token`。
- 前端把 `X-Token` 存进 `localStorage`，之后每个请求都带 `X-Token` 请求头。
- `LoginFilter` 先读请求头，读不到再退回 cookie。

请求头这条通道跟浏览器是否允许写 cookie 无关，所以被拦了也能用。实测：只带 `X-Token` 头、完全不带 cookie 请求 `POST /api/item`，返回 200。

顺带把静态资源的缓存策略改了：`html / js / css` 一律 `no-cache, must-revalidate`。之前是 5 分钟，会出现"代码改了但页面还是旧版"的假象。

### 9. 被弹回登录页时的排查顺序

1. **先强制刷新**：Ctrl + F5（或 Ctrl + Shift + R）。旧 JS 会一直跑旧逻辑。
2. 打开 DevTools → Application → Local Storage，看有没有 `hq.token`。有值说明前端拿到了凭证。
3. DevTools → Network，点开任意一个 401 的请求，看 Request Headers 里有没有 `X-Token`。
4. 如果 `localStorage` 里没有 `hq.token`，说明登录响应头没被读到，检查是否有插件拦截，或换个普通窗口（非无痕）。
5. 确认访问的是 `http://localhost:8080`，不要混用 `127.0.0.1` 和 `localhost`——两者的本地存储和 cookie 是分开的。

### 10. 三条鉴权通道（按可靠性排序）

浏览器环境不可控，所以凭证准备了三份，任意一份活着就能用：

| 通道 | 存放位置 | 能扛住什么 | 失去后 |
| --- | --- | --- | --- |
| 1. 请求头 | 内存 `state.token` | 禁用 Cookie、禁用本地存储都拦不住 | 刷新页面后失效 |
| 2. `localStorage` | `hq.token` | 刷新页面、重启浏览器 | 被清除或禁用站点数据 |
| 3. Cookie | `Set-Cookie: hq_token` | 换标签页、直接输网址 | 被浏览器策略拦掉 |

登录响应会把凭证同时写进这三处（响应体 `token` 字段 / `X-Token` 头 / `Set-Cookie`）。`LoginFilter` 按 请求头 → Cookie 的顺序取，验签通过就放行。

实测：登录成功后用 CDP 清空浏览器所有 Cookie，再点「我的 / 报价 / 交换」，页面照常渲染，不跳登录页。

### 11. 登录报错不再用弹层

之前登录失败会弹 toast，连点几次就叠成一屏红条盖住表单。现在错误显示在卡片内、按钮上方的一行浅红提示里，同时 toast 也加了去重和最多三条的限制。

登录成功后会立刻回调一次 `/api/user/me` 自检，确认会话真的建立起来了；失败才提示"登录没有生效"，而不是让你先跳进去再被弹回来。

### 12. 重置演示数据不能换用户 id

现象：点「我的」弹一句「用户不存在」，其它页面看着正常。

原因：早先的重置逻辑是 `DELETE FROM user WHERE role=0` 再重新插入。用户是被重建的，自增 id 从 101 变成 104，但浏览器里的登录态记的还是 101，`/api/user/me` 拿着这个 id 去查，自然查不到。

现在分两层修：

| 层 | 做法 |
| --- | --- |
| 根因 | `reset()` 不再删用户，改成按学号 upsert。三个演示账号的 id 从第一次创建起就固定不变，重置只清物品、意向、交换单、评价、举报、日志 |
| 兜底 | `LoginFilter` 每个受保护的请求都确认一次「session 里的 userId 在库里还在」。不在就销毁 session，返回 401「登录状态已失效，请重新登录」，前端随即跳登录页 |

所以现在无论哪种情况都不会再看到「用户不存在」：账号还在就是 200，账号没了就是 401 引导重登。

实测：

```
1. 小林登录                    id = 107
2. 管理员重置演示数据           新物品 [116, 117, 118]
3. 小林的旧会话点「我的」        200 success，id 仍是 107
4. 手动把账号从库里删掉
5. 旧会话点「我的」             401 登录状态已失效，请重新登录
6. 旧会话点「报价」             401 同上
```

### 14. 体积与内存

#### 磁盘：1.5G → 4.2M

`du -sh` 一查就露馅：项目 1.5G，其中 1.44G 全在 `target/edge-session`、`edge-repro`、`edge-blocked` 三个目录里。这些是截图脚本的浏览器用户目录，一份 481MB——里面躺着 169MB 的视觉模型文件、156MB 的 crx 缓存、22MB 的 Widevine 解密模块。跟项目代码一毛钱关系没有。

处理两条：

1. 删掉这三个目录，`target` 回到 399K。
2. 改脚本，从根上不再堆积：

```python
profile = tempfile.mkdtemp(prefix="hyq-edge-")
atexit.register(lambda p=profile: shutil.rmtree(p, ignore_errors=True))
```

浏览器配置挪到系统临时目录，进程退出自动删。改完重跑一次截图脚本，`target` 仍然是 399K，`%TEMP%` 下也没有 `hyq-edge-*` 残留。

#### 运行时：304MB → 147MB

原来 JVM 完全按机器内存自动取参数，16G 的机器它就敢要 4G 堆上限，虽然实际用不到，但工作集和私有内存都被撑起来了。加了 `.mvn/jvm.config`：

```
-Xms32m
-Xmx192m
-XX:MaxMetaspaceSize=128m
-XX:ReservedCodeCacheSize=48m
-XX:MaxDirectMemorySize=48m
-XX:+UseSerialGC
-Xss512k
```

几个参数为什么这么设：

| 参数 | 原因 |
| --- | --- |
| `-Xmx192m` | 实测常驻堆 60–80MB，192 留了两倍余量，够跑并发 |
| `-XX:ReservedCodeCacheSize=48m` | 默认 240MB，这个项目编译出来的代码量连 20MB 都用不满 |
| `-XX:MaxMetaspaceSize=128m` | Tomcat + JDBC 驱动 + 自身类，实占约 80MB |
| `-XX:+UseSerialGC` | 单用户演示，不需要 G1 那套并发线程，省下 GC 线程和堆外结构 |
| `-Xss512k` | 每条线程栈减半，工作线程降到 20 条后进一步压缩 |

同时把 Tomcat 的 `maxThreads` 从默认 200 降到 20、`minSpareThreads` 降到 3——这个系统并发是个位数，200 条线程纯属摆排场。

`start.bat` 里不再单独设 `MAVEN_OPTS`，参数只在 `.mvn/jvm.config` 一处，避免两边打架。好处是直接敲 `mvn exec:java` 也生效。

#### 前后对比

| 指标 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| 项目磁盘 | 1.5 GB | 4.2 MB | −99.7% |
| 工作集 | 304.2 MB | 146.9 MB | −52% |
| 私有内存 | 496.5 MB | 142.2 MB | −71% |
| 虚拟内存 | 10022 MB | 4836 MB | −52% |
| Tomcat 线程上限 | 200 | 20 | −90% |

启动时会把实际生效的堆上限打出来，看到 `JVM 堆上限：185 MB，工作线程 20 条` 就说明配置吃上了。

#### 压测过，不是只看数字

- 图片上传 200，`/api/upload` 正常（走的是受 `MaxDirectMemorySize` 限制的那条路）
- 20 个线程并发 200 次请求，全部 200，没有排队排死
- 三方环、我的、物品详情、后台看板，逐一 200

真觉得 192MB 还多，改 `.mvn/jvm.config` 里的 `-Xmx` 就行，改小到 128m 也能跑，但建议留着余量，答辩现场别为了省几十兆把自己卡住。

#### 他人主页

路由 `#/user/{id}`。四个入口：物品详情页的发布人整行、交换单里的参与者名字、评价列表里的评价人、以及手工拼链接。

**隐私**：主页走 `publicProfile`，学号字段在返回前被置空。密码和盐本来就有 `@JsonIgnore`，不进 JSON。

#### 评价的三个入口

| 入口 | 场景 |
| --- | --- |
| 交换单详情 →「给对方打个分」 | 三方交换时先选人再评 |
| 他人主页 →「评价 TA」 | 只在这单还没评时出现 |

`GET /api/review/pending` 是新增的，SQL 用 `NOT EXISTS` 找「我参与完成但没评过对方」的单子，索引走 `exchange_detail(user_id)` 和 `review(exchange_id, from_user, to_user)`。

#### 信用分制度

初始 80，范围 0–100（`LEAST(100, GREATEST(0, ...))` 在 SQL 里夹住，不会越界）。

| 事件 | 变动 |
| --- | --- |
| 完成一次交换（三方或两方，每人各算） | +2 |
| 收到 5 星 | +2 |
| 收到 4 星 | +1 |
| 收到 3 星 | 0 |
| 收到 2 星 | −1 |
| 收到 1 星 | −2 |
| 待交付超过 7 天未确认 | −3 |
| 物品被管理员认定违规 | −5 |

评级：优秀 ≥ 90、良好 ≥ 80、一般 ≥ 70、较低 ≥ 60、受限 < 60。**低于 60 分不能发布物品、不能发起报价、不能用换物环**，三处都有独立校验。

这次补的一条是「物品被认定违规扣物主 5 分」——之前举报成立只下架物品，物主一点代价都没有，等于信用分只是墙上的装饰。


新库依次执行 `sql/schema.sql`、`sql/auction.sql`、`sql/auction_review_migration.sql`。后两份分别创建拍卖表并添加审核字段；迁移文件仅适用于尚未添加这些字段的数据库，执行前先备份。既有部署的物品和拍卖数据不会被迁移脚本清空。新提交的物品必须包含已上传的有效图片，经管理员审核后公开。按最新的非现金交易要求，现金竞拍的新建、出价和结算已停用；历史记录保留。

## 社区与自动审核

在原有数据库迁移完成后，依次运行 `sql/item_review_timer_migration.sql` 和 `sql/community.sql`。物品使用独立的审核提交时间，待审超过五分钟且图片有效时由定时任务自动上架；现金拍卖已停用，不再自动审核拍卖。定时任务约每十秒检查一次，管理员已处理的记录不会被覆盖。公共聊天室需登录，支持文字、单张图片和本人在架物品分享，展示最近 100 条；Scrap Arena 使用 `src/main/webapp/scrap-arena/` 下的独立游戏文件。


## 闭环与社区扩展

在已有数据库上，先备份，再依次执行 `sql/notifications_demo.sql` 与 `sql/community_exchange.sql`；迁移中的 `ALTER TABLE` 不可重复执行。200 条示例商品由 `scripts/generate_demo_catalog.py` 和 `demo-catalog/seed.py` 生成及幂等导入，均标记为不可交易的示例。向量检索使用服务器本地的量化 BGE 中文模型和 `semantic/server.py`，不向外部发送查询；服务只监听 127.0.0.1:18084。

物品可多选期望品类，选择仅一对一、主动找环或等待自动匹配；被动匹配仅发送候选通知，不替用户创建交换单。三方闭环需全部确认后进入交付，参与者可通过独立协商房间沟通。私聊按物品和双方独立隔离；求换信息不等同于已上架物品。校园实名认证、跨校区认证、积分兑换、N 人闭环及交付照片担保尚未实现。

## 搜索与语义检索

搜索走 `GET /api/item/search`，返回结构不变，`searchMode` 说明本次是 `semantic` 还是 `keyword`。语义侧车不可用时接口不再报 503，而是自动按关键词检索，前端无需改动。

侧车启动：Windows 双击 `semantic\run_local.bat`（首次会自动建 `semantic\.venv` 并装依赖），Linux 用 `semantic/server.py`。连接信息一律从 `DB_URL` 解析主机、端口、库名，不再写死 3306；健康检查 `http://127.0.0.1:18084/health` 出现 `"ready": true` 后才开始提供语义结果。

截断参数决定「搜得准不准、结果多不多」，都可用环境变量覆盖，不必改代码：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `SEMANTIC_SCORE_FLOOR` | 0.45 | 相关度绝对下限，低于它的条目直接不返回 |
| `SEMANTIC_SCORE_MARGIN` | 0.05 | 允许低于首条多少分，控制结果集宽度 |
| `SEMANTIC_KEEP` | 30 | 单次最多返回条数 |
| `SEMANTIC_REFRESH_SECONDS` | 30 | 索引重建间隔 |

旧版只有一个 0.35 的固定阈值，无关条目也普遍落在 0.35 至 0.45，导致每次搜索都返回几十条噪声。改为「绝对下限 + 相对首条容差 + 条数上限」后，具体商品查询从平均 22 条降到 2 条，无对应商品的查询返回空列表，正确条目仍全部保留。标定脚本 `semantic/_probe/bench_rank.py`，端到端验证 `semantic/_probe/verify_search.py`，两者只读本地数据，可重复运行。

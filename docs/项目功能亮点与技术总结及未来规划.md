# 换一圈（HuanYiQuan）— 项目功能全景、核心亮点、技术难点与未来演进规划

> 本文档基于当前项目（正式版 `v2.1`）实际源码与架构梳理编写，全面盘点已实现业务功能、产品与工程亮点、核心技术难点及后续演进路线。

## 一、项目技术栈与架构概览

| 层次 | 实际选型 | 说明 |
| --- | --- | --- |
| **应用载体** | Java 11+ / Jakarta Servlet 6.0 / 内嵌 Tomcat 10.1.24 | `Application.java` 启动内嵌 Tomcat，工作线程上限 60，支持 `mvn exec:java` 直跑与 `war` 包部署 |
| **数据与连接池** | MySQL 8.0 + 原生 JDBC + HikariCP（`DBUtil`） | 最大连接池 20、最小空闲 4，开启 `PreparedStatement` 缓存，全部写操作手动事务控制 |
| **前端双端体系** | 原生 HTML5 / CSS3 / ES6+（零构建工具） | `src/main/webapp/`（桌面逛街式主站）与 `src/main/webapp/mobile/`（移动端独立 H5）分离适配 |
| **语义检索侧车** | Python 3 + ONNX Runtime + 量化 BGE 中文模型 + `pymysql` | 独立进程监听 `127.0.0.1:18084`（`semantic/server.py`），不可用时自动无缝降级 SQL 检索 |
| **AI 视觉能力** | DeepSeek V4.1 Flash 多模态视觉接口 | `AiVisionService.java` 通过 Java `HttpClient` 调用，支持图片估价与拍照搜图识物 |
| **异步发信与调度** | `ScheduledThreadPoolExecutor` + Python SMTP 子进程 | `TaskListener` 维护后台定时任务；`EmailVerificationService` 隔离调用 `scripts/send_verification_email.py` |

## 二、全部已实现功能清单

### 1. 账号体系、安全认证与双端适配
- **学号注册与加盐口令**：校验 10 位数字学号（`^\d{10}$`），`PasswordUtil` 采用 8 字节 `SecureRandom` 随机盐 + SHA-256 哈希存储。
- **邮箱验证与多模式登录**（`AuthEntryServlet`、`EmailVerificationService`）：
  - 支持账号密码登录、绑定邮箱后邮箱密码登录、邮箱验证码免密登录、注册邮箱验证码校验。
  - 后端基于数据库 challenge 表实现 **60 秒发送间隔防刷**，前端桌面端与移动端登录页统一配备 **90 秒验证码发送倒计时**。
- **跨重启登录态恢复**：在内存 `HttpSession` 基础上由 `TokenUtil` 签发 7 天有效期的 `hq_token`（`userId.expireAtMillis.HmacSHA256`）签名凭证，服务端重启后 `LoginFilter` 自动还原会话；被封禁账号在请求拦截阶段即销毁旧会话并返回 401。
- **双端自动路由分流**：`mobile-entry.js` 结合设备 UA、触控能力与视口宽度自动将移动设备导向 `/mobile/index.html`，并支持 `?view=desktop` / `?view=mobile` 强制切换。

### 2. 商品发布、双轨交易与生命周期管理
- **双轨交易模式**（`ItemService`）：支持 **明码标价**、**以物换物** 与 **可买可换双轨并行**（含入手原价、标价、品牌、校内交接方式、是否接受议价及换物意向品类/指定物品）。
- **分类与成色体系**：覆盖 7 大校园核心分类（教材、数码、运动、生活、衣物、绿植、其他）与 4 级成色（全新、九成新、七成新、有使用痕迹）。
- **发布风控校验**：要求用户信用分 ≥ 60、单人同时在架物品 ≤ 20 件、必须校验有效上传图片（`ImageCheck`）、全字段敏感词过滤（`SensitiveWordDao`）及短时间同名去重。
- **自动审核与上下架**：用户可随时编辑、下架或重新上架；新提交物品进入待审核态（`status=5`），超过 **5 分钟**未被人工干预且图片有效时由 `AutoReviewService` 自动审核上架，并同步触发异步被动找环。

### 3. 交易核心：一对一报价、三方换物环与交换单闭环
- **一对一报价系统**（`OfferService`）：
  - 支持选物发起报价、接收方**接受 / 拒绝 / 撤回 / 反向还价**（关闭原报价并生成 `parent_id` 指回原报价的新报价）。
  - 报价 **24 小时**未处理由定时任务自动置为失效。
- **主动找环与正式成环**（`CycleService`）：
  - 发起方查看匹配候选时，系统检索 `I0(我) → B(I1) → C(I2) → A` 三方闭环（融合显式 `intent` 意向与接力心愿 `WishService.RelayWish`），最多返回 3 组候选。
  - 确认落单后同时锁定 3 件物品，生成 `type=3` 三方交换单。
- **被动成环候选推送**（`PassiveMatchService`）：新物品过审即启动守护线程即时探测，同时后台每 60 秒分批游标扫描，发现可成环组合时向三方推送系统通知（只通知不擅自替用户锁单）。
- **交换单状态机与违约控制**（`ExchangeService`）：
  - **严格单向推进**：待确认（三方需在 **24 小时**内全部确认，否则整单解散并解锁物品）→ 待交付 → 约定校园面交点与时间段 → 全员确认交付完成（或 **7 天**交付超时自动关闭并扣减未交付方信用分）。
  - 任意阶段合法取消均在事务内整单作废并解锁关联物品；关键状态流转全部写入 `biz_log` 审计表。
- **评价与信用分体系**（`ReviewService`、`UserService`）：初始信用分 `80`，成交加分、互评星级动态微调，支持在他人主页查看信用变动明细与好评率（且隐藏学号隐私）。

### 4. 校园特色聚合频道（桌面端 Goldbox 集成 `#/idle`）
- **校园拍卖**（`AuctionService`、`AuctionServlet`）：发布 1~168 小时竞拍品（需图片与敏感词校验），`BigDecimal` 精确金额校验，事务内行锁判定出价递增，支持发布者选标结算及后台审核/5 分钟自动过审。
- **求换专区与换物接力**（`WishService`、`WishMatchService`）：发布求换心愿并支持捆绑自身在架闲置作为换物筹码（`wish_offer`）；后台每 **20 秒**自动将心愿与全校在架商品进行标题标准化匹配并双向发送通知。
- **AI 好物估价与拍照搜图**（`AiVisionService`、`AiServlet`）：
  - 前端提供取景框式上传与实时进度动画，后端调用多模态模型识别物品品类、成色、建议人民币区间与保值亮点标签。
  - 支持拍图识别 2~6 字核心商品关键词直接发起全站检索。

### 5. 校园社交、即时沟通与社区娱乐
- **按物品与双方隔离的私聊系统**（`ConversationService`）：围绕具体物品建立 `item_conversation`，支持文字与单张图片消息，桌面端呈现 3 栏式 IM 界面，进入会话自动清除对应未读通知。
- **三方闭环专属协商房间**（`ring_message`）：仅当前三方交换单的三名当事人可进入，用于集中协商校内交接时间与地点。
- **社区贴吧与街机小游戏**（`CommunityService`、`scrap-arena/`）：多聊天室支持文字、图片及个人真实在架物品卡片分享；内置独立 HTML5 格斗休闲游戏 *Scrap Arena*。
- **关注、收藏、足迹与通知中心**：支持关注卖家/同学（`FollowersServlet`）、商品收藏（`social_favorite`）、浏览足迹（`social_history`）、个人隐私/设置开关（`user_settings`）及分类站内信通知（`NotificationService`）。

### 6. 混合智能搜索与运营管理后台
- **语义 + 词面混合搜索**（`SemanticSearchService` + `semantic/`）：集成意图解析、规格边界匹配、BGE 向量检索与 SQL `LIKE` 召回兜底。
- **管理员后台**（`AdminService`、`AdminFilter`）：举报审核与违规下架处理、用户封禁/解封、活动与交易流水查看、核心指标看板（成交量、成环成功率、热门分类）以及演示数据一键生成（`DemoService`、`demo-catalog/`）。

## 三、核心产品与工程亮点

1. **解决“一对一换物死锁”的三方闭环算法 + 接力体系**
   - 校园闲置最大的痛点是双方“互有所需”概率极低。项目通过将显式换物意向（`intent`）与接力心愿（`wish_offer`）统一抽象成物品有向图，用三方闭环 + 被动候选推送把“低频偶遇”变成可计算的“主动匹配”。
2. **极轻量化、零构建依赖的纯净技术架构**
   - 后端不使用 Spring/MyBatis 等重型框架，原生 Servlet + HikariCP + 内嵌 Tomcat 即可单命令运行或打 WAR 包上线，资源占用极低，适合高校学生服务器/轻量云部署。
   - 前端零构建链路（无需 Webpack/Vite/Node 运行时），改完静态资源即可直接上线生效。
3. **隐私友好的本地化 AI 向量检索（ONNX Runtime + BGE）**
   - 校内商品库与学生求换意图无需上传第三方云向量库，完全在服务器本地 CPU 运行量化 BGE ONNX 模型，结合自研意图解析与词面融合排序，兼顾隐私安全与搜索精准度。
4. **双端各司其职的精细化 UI 设计**
   - **桌面端** 1:1 对标成熟购物平台逛街式体验：双层深青顶栏、`≡ 全部` 左侧全部分类抽屉、5:8 顶部推广海报条、4 列圆角逛街面板、独立 Goldbox 式校园闲置频道与 3 栏私聊窗。
   - **移动端** 完全遵循单手触控逻辑与轻量卡片流设计，配备独立拍照估价取景框与贴吧聊天室。
5. **高可用兜底与安全边界意识**
   - 语义侧车挂掉时 `SemanticSearchService` 1 秒超时自动平滑降级为关键词召回，不会导致搜索功能雪崩。
   - 邮件发送隔离至 Python 短生命周期子进程并设 18 秒强杀上限，失败自动回滚验证挑战记录，避免阻塞 Tomcat 线程池。

## 四、核心难点技术解析

### 1. 三方并发锁物与死锁消解（`CycleService` & `ExchangeService`）
- **难点**：三方成环涉及跨 3 个用户的 3 件商品同时锁定，若多个用户并发发起包含重叠物品的三方环，极易出现“交叉加锁导致 MySQL 死锁”或“一件物品同时被两条交换单锁走”。
- **解法**：
  - 搜索阶段只读不锁，并设置单次最大检查组合上限 `MAX_CHECK = 300`，防止关系图密集时拖死数据库。
  - 正式落单进入 `DBUtil.tx()` 手动事务后，**先对 3 个物品 ID 执行升序排序（`Arrays.sort(ids)`）**，再按固定顺序执行 `SELECT status FROM item ... FOR UPDATE` 悲观行锁，从根源上破坏加锁等待环路，避免数据库死锁。
  - 确认与交付阶段同样先在事务内通过 `FOR UPDATE` 复核 `exchange.status` 与单人确认位，确保状态机严格单向推进。

### 2. 被动匹配与心愿匹配的“防重防抖 + 幂等通知”（`PassiveMatchService` & `WishMatchService`）
- **难点**：定时任务每隔 20~60 秒扫描数据库，如何防止对同一组物品反复发送轰炸式通知？如果扫描期间物品刚刚被修改或下架如何保证不发错通知？
- **解法**：
  - 引入“审核世代（`review_submitted_at`）”概念：将排序后的 3 件物品 ID 与各自世代拼接计算 **SHA-256 摘要作为 `ring_key`**。
  - 事务内再次 `FOR UPDATE` 校验三件物品仍在架且世代未变后，利用 `ring_match_notice(ring_key)` 主键唯一约束配合 `INSERT IGNORE` 实现严格幂等去重（心愿匹配同理使用 `(wish_id, item_id)` 唯一约束）。

### 3. 本地 BGE 语义检索“噪音过多与实体边界误伤”治理（`semantic/server.py` & `retrieval.py`）
- **难点**：
  1. 早期仅使用单一固定余弦分数阈值（0.35），导致大量无关商品落在 `0.35 ~ 0.45`，单次具体查询返回二十余条噪音；
  2. 口语化长句（如“预算 200 以内只换不卖的宿舍护眼台灯”）干扰向量编码方向，且数字型号易误召回（如搜 `iPhone 13` 命中 `iPhone 130`）；
  3. 后台全量刷新索引若每次重算所有商品向量会拉高 CPU 负载。
- **解法**：
  - **结构化意图剥离**：`parse_intent` 正则抽取预算上限与交易模式（只买/只换）在打分前先做硬性过滤，剥离口语前缀/后缀并识别数字型号边界（后继非数字）与存储容量最低要求（`>=`）。
  - **向量 + 词面 RRF 融合与双重截断**：`fuse()` 将精确标题词面分级与 BGE 向量倒数排名融合；向量分支采用 **“绝对下限 `FLOOR=0.45` + 相对首条容差 `MARGIN=0.05` + 条数上限 `KEEP=30`”** 的动态截断，压低长尾噪音同时保留真实相关项。
  - **SHA-256 增量向量缓存**：每 30 秒刷新索引时先比对物品文本哈希，仅对新增或变更商品执行批量推理（batch=16），并基于读写可重入锁（`RLock`）保证并发查询安全。

### 4. 无容器依赖下的并发限流与跨重启会话连续性
- **并发限流**（`RateLimiter` + `SecurityFilter`）：不依赖 Redis，在内存中使用 `ConcurrentHashMap<String, Window>` + `AtomicInteger` 实现线程安全固定时间窗口限流（AI 接口 12 次/分、认证接口 20 次/分、上传接口 25 次/分），并设置 20,000 桶上限与周期清理防内存泄漏；同时优先读取 `X-Forwarded-For` / `X-Real-IP` 以适配反向代理后的真实限流。
- **会话恢复**（`TokenUtil` + `LoginFilter`）：内嵌 Tomcat 重启会清空内存 `HttpSession`，系统同时向客户端签发防篡改 HMAC-SHA256 Token Cookie，当请求命中未登录拦截时自动验签并重建会话与鉴权上下文，保证线上热更新/重启不掉线。

## 五、未来该做什么（演进路线图）

### 阶段一：近期必做（生产安全加固与代码工程化）
1. **密码哈希与密钥安全强化**
   - 将 `PasswordUtil` 的加盐 SHA-256 升级为抗暴力破解的慢哈希算法（**BCrypt** 或 **Argon2id**），并在用户下次登录时平滑迁移旧密码摘要。
   - 在生产部署启动脚本中强制要求注入高强度随机 `APP_SECRET` 环境变量，避免默认 fallback 密钥 `huanyiquan-local-secret` 暴露风险。
2. **前端大文件拆分与工程化规范**
   - 当前桌面端 `src/main/webapp/app.js`（已超 6,300 行）与 `desktop-amazon.css` 体积较大，单文件维护成本升高。建议保持原生 ES Modules（`<script type="module">`）按功能域拆分（`router.js`、`home.js`、`idle.js`、`chat.js`、`me.js` 等），无需引入复杂打包器即可实现清晰的模块化维护。
3. **媒体存储升级与图片压缩**
   - 完善 `UploadServlet`：接入图片上传前/后异步压缩与多规格缩略图生成（WebP），解决高清原图导致列表首屏加载偏慢的问题；中大规模部署时将本地 `uploads/` 目录迁移至对象存储（OSS/COS/MinIO）。
4. **全面分页与自动化测试 CI**
   - 为目前硬编码 `LIMIT 100` 的拍卖列表、报价列表、交换单及聊天消息接口补充游标分页（cursor pagination）。
   - 在 GitHub 仓库配置 **GitHub Actions CI**：每次提交自动运行 `mvn test`、前端 JS/CSS 语法校验及核心 API/语义检索回归脚本（`scripts/health.py`、`scripts/e2e.py`、`semantic/_probe/`）。

### 阶段二：中期迭代（实时体验与核心业务补全）
1. **Jakarta WebSocket 实时通信升级**
   - 替换当前桌面端私聊 IM、社区聊天室与顶部通知红点的定时轮询（`setInterval`），直接利用内嵌 Tomcat 内置的 Jakarta WebSocket API 实现双向实时消息推送、已读回执与竞拍实时出价广播。
2. **校园身份核验与线下交易闭环增强**
   - 接入高校官方邮箱域白名单校验或人工学生证/校园卡核验标识（展示“校内实名认证”徽章）。
   - 在交换单“确认交付”节点增加**校内面交现场照片存证**（可选上传）及争议申诉仲裁工单流转。
3. **多节点自适应换物环与接力规则优化**
   - 在三方环基础上探索可控范围内的 **2~4 人自适应闭环**；引入时间窗自动退环惩罚权重与候选排序优化（综合距离、宿舍楼栋接近度、双方历史交付响应率与信用分排序）。

### 阶段三：长期规划（开源生态化与数据智能）
1. **Docker Compose 一键编排与多校可配置化**
   - 编写标准 `Dockerfile` 与 `docker-compose.yml`（编排 MySQL 8 + Java 主应用 + BGE 语义检索侧车 + Nginx HTTPS），让开源社区其他高校同学或开发者一行命令即可完成全栈拉起。
   - 将写死于前端文案与基础配置的“校名、书院/宿舍楼栋列表、分类与品牌预设”抽象为独立配置表或 JSON 配置中心，支持多校开源复刻与分校区隔离。
2. **基于历史数据的智能推荐与估价微调**
   - 结合站内真实历史成交记录与用户行为日志（`social_favorite`、`social_history`），在本地检索侧车上增加轻量级个性化推荐排序（同专业教材偏好、同楼栋就近流转加权）以及校内二手价格区间实时统计基线，进一步提高 AI 好物估价的校内贴合度。

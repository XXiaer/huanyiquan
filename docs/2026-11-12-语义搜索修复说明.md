# 语义搜索问题定位与修复说明

日期 2026-11-12　范围 `semantic/server.py`、`SemanticSearchService`、`ItemDao`

## 现象

搜索能用，但搜索结果里混进大量不相关商品，而且一次返回几十条。举例（200 条示例商品的本地库）：
搜「电饭煲」返回便携餐盒，搜「iPhone 13」返回 USB 集线器和 Java 程序设计的教材，搜「机械键盘」返回 14 条，
搜「高等数学课本」直接返回 30 条（数据库当时总共就 200 多条在架）。

## 根因

### 1. 截断策略只有一个固定阈值 0.35（主因）

`semantic/server.py` 原先用 `scores >= 0.35` 过滤，然后把命中的全部返回。问题是这个量化 BGE 模型对
**任意**文本对都能给出 0.30 至 0.45 的余弦相似度，无关条目因此大面积越过阈值：

- 200 条商品的库上，15 个「库里根本没有这件东西」的查询平均返回 9.2 条，73% 的查询返回超过 2 条；
- 所有查询平均返回 21.9 条，用户看到的就是一屏噪声。

阈值单独调高也不解决问题：调到 0.50 时，改写查询（「高数课本」→ 高等数学教材）的召回掉到 87%。
0.35 和 0.50 之间不存在一个能同时兼顾召回和精度的点，必须引入相对截断。

### 2. 侧车连数据库时写死 127.0.0.1，且漏传端口

```python
pymysql.connect(host='127.0.0.1', user=..., password=..., database=DB_NAME, ...)
```

`port` 没传，pymysql 用默认 3306；而本项目 `db.properties` 配的是 `127.0.0.1:3307`。
只要 MySQL 不在 3306，侧车索引永远建不起来，`/health` 一直 `ready: false`，`/search` 一直 503，
整条语义检索链路静默失效，只剩前端的关键词兜底。本地实测报错：
`OperationalError (1045, "Access denied for user 'root'@'localhost'")`——它连的是 3306 上的另一个实例。

### 3. 语义服务不可用直接抛 503

`SemanticSearchService` 把 `/search` 的任何异常都转成 `BizException(503)`，搜索整体失败，
由前端两套实现各自兜底（桌面端 `keywordFallback`、手机端 try/catch）。后端明明有数据库可以做关键词检索，
却把一个可选组件当成了强依赖。

### 4. 命中后全表捞一万条再过滤

```java
ItemDao.list(category, condition, null, null, null, Const.ITEM_ON, 0, 10000)
```

为了套分类/成色筛选，把在架物品一次取一万条到内存。超过一万条的在架库会被静默截断，
命中项可能被截掉；每次搜索还要拖全表加 `user` 关联。

### 5. 模型维度写死 384

代码里 `np.empty((0,384))`，实际模型输出 512 维。当前只在空索引分支生效所以没炸，但属于埋着的雷。

## 改动

### `semantic/server.py`

- 数据库主机、端口、库名一律从 `DB_URL` 解析，可被环境变量覆盖；端口不再写死。
- 模型目录默认取仓库内 `semantic-model`，本地不再需要 `SEMANTIC_MODEL_DIR`。
- 截断改成三层：`SEMANTIC_SCORE_FLOOR`（绝对下限，默认 0.45）+ `SEMANTIC_SCORE_MARGIN`
  （相对首条容差，默认 0.05）+ `SEMANTIC_KEEP`（条数上限，默认 30）。首位都低于下限时直接返回空列表，
  让调用方回退关键词检索。
- 维度改为从模型输出读取；`/search` 内部异常返回 503 而不是断开连接。
- 参数全部可用环境变量覆盖，便于按数据量再调。

### `SemanticSearchService`

- 语义命中后按 id 批量取物品（新增 `ItemDao.listByIds`），不再全表捞一万条；分类/成色在内存里对几十条过滤。
- 语义服务不可用时不再 503：自动按关键词检索，正常返回 200。
- 语义结果之外并上关键词命中（`LIKE` 命中即精确相关），保证型号、书名这类具体词不会因为语义分数低被丢掉；
  结果总数封顶 40。
- 返回体结构不变，`searchMode` 区分 `semantic` / `keyword`。

### 其它

- `semantic/run_local.py` 与 `run_local.bat`：本地一键起侧车，自动读 `db.properties`、自动建 venv 装依赖。
- `semantic/_probe/`：三个只读脚本，可重复运行——
  `bench_rank.py`（离线标定截断参数）、`probe_sidecar.py`（侧车连通性）、
  `verify_search.py`（临时库 + 真后端的端到端验证，含新旧配置对比）。

## 验证

`semantic/_probe/verify_search.py` 在独立 MySQL（非 3306 端口）+ 独立 Java 实例上跑通全部用例：

```
sidecar(new): {"ready": true, "items": 200, "error": "", "dim": 512, "floor": 0.45, "margin": 0.05}
PASS  q=机械键盘        2 条  mode=semantic
PASS  q=高等数学课本     2 条  mode=semantic
PASS  q=kindle         2 条  mode=semantic
PASS  q=电饭煲          0 条
PASS  q=投影仪          0 条
PASS  q=机械键盘 category=数码 size=1  total=2 hasMore=True
PASS  q=iPhone 13 命中真实商品 ['iPhone 13 128G 国行']
PASS  语义服务不可用 → mode=keyword，仍返回 200
```

同一批查询的新旧对比（201 条在架）：

| 查询 | 旧（0.35 无相对截断） | 新（0.45 / 0.05） |
| --- | --- | --- |
| 机械键盘 | 14 | 2 |
| 高等数学课本 | 30 | 2 |
| 考研 | 30 | 2 |
| 书 | 31 | 19 |
| 运动 | 32 | 15 |
| 电饭煲 | 2 | 0 |
| 投影仪 | 17 | 0 |
| **平均** | **22.3** | **5.7** |

离线标定（100 个商品名 + 15 个改写说法 + 15 个库里没有的商品）显示：
商品名查询首位命中 100%、改写说法前三条命中 100%、库里没有的商品返回 0 条。
「书」「运动」这类宽泛词仍然返回十几条，属于正常——它们确实匹配到十几件书和运动用品。

## 仍需你确认的一件事

本机 `src/main/resources/db.properties` 指向 `127.0.0.1:3307`，但当前机器 3306 上才有 MySQL 在监听，
3307 无人监听。也就是说双击 `start.bat` 起后端、或起语义侧车，都会连不上库
（侧车 `/health` 返回 `Can't connect to MySQL server ... 由于目标计算机积极拒绝`）。

这条我没动，因为不清楚你要连的是哪个实例、密码是什么。二选一即可：

- 把 MySQL 起到 3307；或
- 把 `db.properties` 改回 3306，并填上正确密码（仓库里的 `db.properties.bak` 是 3306 + ROOT，但该密码在本机验证不通过）。

## 还没做

- 手机端搜索结果页在 `size=40` 下做客户端二次筛选，宽泛词时仍会排出较多卡片；本次按「只改后端与侧车」范围未动前端。
- 没有引入真正的 BM25 权重与向量混排打分（实测字面加权在这份语料上反而降低召回，见 `bench_rank.py` 输出），
  当前是「严格语义截断 + 关键词并集」的轻量混排。
- 词表级同义词、查询改写、点击反馈排序都未做。
